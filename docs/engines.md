# Шаблонизаторы

Исходники шаблонов от шаблонизатора не зависят: его задаёт опция `engine`.

| Шаблонизатор | Импорт               | Расширение | Для чего                                           |
| ------------ | -------------------- | ---------- | -------------------------------------------------- |
| Handlebars   | `vitempl/handlebars` | `.hbs`     | серверы, которые читают шаблоны во время работы    |
| askama       | `vitempl/askama`     | `.html`    | сервер на Rust: шаблоны компилируются вместе с ним |
| Jinja        | `vitempl/jinja`      | `.html`    | Jinja2 (Python) и совместимые с ним движки         |

```ts [vite.config.ts]
import { askama } from "vitempl/askama";

export default defineConfig({
  plugins: [vitempl({ engine: askama() })],
});
```

## Компоненты в askama и Jinja

Оба шаблонизатора устроены вокруг макросов, поэтому компонент становится макросом `render`, а его параметры — теми данными, к которым компонент обращается:

```vue
<!-- partials/ListItem.vue -->
<template>
  <li>{{ title }}</li>
</template>
```

```jinja
{# partials/ListItem.html #}
{% macro render(title) %}<li>{{ title }}</li>{% endmacro %}
```

Вызывающий шаблон импортирует компонент и передаёт props по именам — в askama через `::`, в Jinja через `.`:

```jinja
{% import "partials/ListItem.html" as partials_list_item %}
{{ partials_list_item::render(title=item.title) }}
```

Из этого следуют два правила сборки:

- **Компонент получает только то, что использует.** Props, к которым шаблон компонента не обращается, не передаются: макрос не примет лишний аргумент.
- **Данные, которые компонент использует, обязан передать вызывающий.** Иначе сборка остановится с ошибкой, в какой компонент и каких данных не хватает.

Слот компонента превращается в `caller()`, а содержимое передаётся блоком `{% call %}`:

```jinja
{% macro render() %}<main>{{ caller() }}</main>{% endmacro %}
{% call layouts_layout::render() %}<h1>{{ title }}</h1>{% endcall %}
```

Страница и фрагмент в макрос не оборачиваются: их данные готовит сервер, а слот в них не поддерживается.

## Условия

В Jinja условием может быть любое значение — пустая строка и `none` считаются ложью. В askama условие превращается в условие Rust, поэтому оно обязано быть `bool`. Чтобы шаблоны работали одинаково в обоих, условия пишутся явно:

| В шаблоне             | askama                           | Jinja                       |
| --------------------- | -------------------------------- | --------------------------- |
| `v-if="admin"`        | `{% if admin %}`                 | `{% if admin %}`            |
| `v-if="!admin"`       | `{% if !admin %}`                | `{% if not admin %}`        |
| `v-if="user != null"` | `{% if let Some(user) = user %}` | `{% if user is not none %}` |
| `v-if="user == null"` | `{% if user.is_none() %}`        | `{% if user is none %}`     |
| `v-if="page > 1"`     | `{% if page > 1 %}`              | `{% if page > 1 %}`         |

Проверка `!= null` в askama связывает значение с именем, и внутри ветки путь к нему заменяется на это имя: `page.user != null` даёт `{% if let Some(user) = page.user %}`, а `{{ page.user.name }}` внутри становится `{{ user.name }}`.

Условия объединяются `&&` и `||`, но проверку на null сочетать с другими условиями нельзя: в Rust такое условие ещё не поддерживается.

## Чем askama отличается

- **Шаблоны компилируются вместе с сервером.** Сервер не читает папку шаблонов во время работы — они попадают в бинарник, а данные приходят из структуры Rust. Поэтому после пересборки шаблонов сервер нужно собрать заново; cargo замечает изменения шаблонов сам.
- **Компонент не может подключать сам себя.** askama разворачивает макросы при компиляции и на рекурсии останавливается («Found recursion in macro calls»), поэтому сборка сообщает об этом заранее. Косвенную рекурсию (A подключает B, B подключает A) плагин не видит — она всплывёт при сборке сервера.
- **Макрос видит данные вызывающего шаблона.** В отличие от Jinja, где импортированный макрос контекста не видит, в askama компонент может обратиться к данным страницы. В собранных шаблонах этого не происходит: плагин передаёт параметрами всё, что компонент использует, и имена параметров перекрывают данные вызывающего.
- **Экранирование выбирается по расширению** `.html`.

## Чем отличается Jinja

- **Экранирование включает сервер.** Jinja2 по умолчанию не экранирует: при настройке окружения нужен `autoescape` (например, `select_autoescape(["html"])`), иначе данные попадут в HTML как есть.
- **Рекурсия разрешена.** Компонент, который подключает сам себя, вызывает свой макрос напрямую, без импорта.

## Свой шаблонизатор

Адаптер — объект с генератором шаблона; как он устроен и что получает, описано в разделе [Сборка](./build#шаблонизатор). Адаптеры askama и Jinja собраны из общего генератора jinja-подобных шаблонов, который отличается описанием диалекта: ключевыми словами, разделителем при вызове макроса и работой с необязательными значениями.
